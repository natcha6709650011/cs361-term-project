# Room Reservation & Utilization Management System

## Project Vision

สร้างระบบกลางที่ช่วยให้ผู้ใช้งานสามารถเข้าถึงข้อมูลห้องได้อย่างสะดวกและเป็นระบบ โดยมีข้อมูลเกี่ยวกับประเภทห้อง ความจุ อุปกรณ์ สิ่งอำนวยความสะดวก เงื่อนไขการใช้งาน และกติกาการจอง เพื่อเป็นพื้นฐานสำหรับการพัฒนาระบบค้นหา จอง อนุมัติ และติดตามการใช้ห้องใน Version ถัดไป

---

## V1 – Information

### Objective

V1 มุ่งเน้นการให้ผู้ใช้สามารถเข้าถึงข้อมูลพื้นฐานของห้องได้ โดยยังไม่จำเป็นต้องเข้าสู่ระบบ

### In Scope

ผู้ใช้สามารถดูข้อมูลพื้นฐานของห้อง เช่น

- ประเภทห้อง
- ความจุ
- อุปกรณ์
- สิ่งอำนวยความสะดวก
- เงื่อนไขการใช้งาน
- กติกาการจอง

### Out of Scope

ฟังก์ชันต่อไปนี้ยังไม่อยู่ใน V1:

- การเข้าสู่ระบบและ Authentication
- การสร้าง แก้ไข หรือยกเลิกการจอง
- การอนุมัติการจอง
- การจัดการข้อมูลห้องโดย Admin
- การบันทึก Check-in / No-show
- การบันทึก Actual Usage
- การวิเคราะห์ Utilization
- Dashboard สำหรับผู้ดูแลหรือผู้บริหาร

ฟังก์ชันเหล่านี้จะพัฒนาตาม Requirements ของ V2–V7

### Assumptions / To Validate

- ข้อมูลห้องในปัจจุบันมาจากไหน?
- ข้อมูลห้องที่มีอยู่สามารถนำมาใช้ในรูปแบบ Spreadsheet, Database หรือ API ได้ไหม?
- ข้อมูลห้องและข้อมูลการจองมีการอัปเดตบ่อยแค่ไหน?
- V1 จำเป็นต้องแสดงสถานะห้องว่างแบบ Real-time หรือไม่?

### Data Ownership / Source of Truth

- ระบบ V1 จะเน้นการนำข้อมูลห้องที่มีอยู่เดิมมาแสดง มากกว่าการสร้างข้อมูลใหม่ผ่านระบบ
- ระบบควรเชื่อมต่อหรือรับข้อมูลจากแหล่งข้อมูลเดิม หากสามารถทำได้
- ผู้ดูแลและแหล่งข้อมูลหลัก (Source of Truth) ยังต้อง Validate

### Boundary

#### Inside the System – V1

ระบบ V1 รับผิดชอบการ:

- แสดงข้อมูลพื้นฐานของห้อง
- แสดงประเภทและความจุของห้อง
- แสดงอุปกรณ์และสิ่งอำนวยความสะดวก
- แสดงเงื่อนไขการใช้งาน
- แสดงกติกาการจอง

#### Outside the System – V1

สิ่งที่ยังอยู่นอกขอบเขตของ V1 ได้แก่:

- Authentication / Login
- การสร้างและจัดการการจอง
- การอนุมัติการจอง
- การจัดการข้อมูลห้องโดยผู้ดูแล
- การบันทึก Check-in / No-show
- การบันทึก Actual Usage
- การวิเคราะห์ Utilization
- Dashboard และสถิติการใช้ห้อง
- การสร้างหรือแก้ไขข้อมูลในแหล่งข้อมูลต้นทาง

### External Actors

สำหรับ V1 มี External Actor หลักคือ:

- ผู้ใช้ทั่วไป — เข้าถึงและดูข้อมูลพื้นฐานของห้องโดยไม่จำเป็นต้องเข้าสู่ระบบ

บทบาทอื่น เช่น นักศึกษา อาจารย์ เจ้าหน้าที่ และผู้ดูแลระบบ จะเข้ามามีบทบาทใน Version ถัดไป เมื่อระบบรองรับ Authentication, Reservation และ Management

### External Systems / Data Sources

ระบบอาจรับข้อมูลห้องจากแหล่งข้อมูลที่มีอยู่เดิม เช่น:

- Spreadsheet
- Database
- API
- หรือแหล่งข้อมูลอื่นของสาขาวิชา

รูปแบบและแหล่งข้อมูลหลักที่แน่นอนยังต้อง Validate

### System Boundary

#### ผู้ใช้ → ระบบ V1

ผู้ใช้สามารถ:

- ขอข้อมูลห้อง
- ดูรายละเอียดห้อง

#### ระบบ V1 → ผู้ใช้

ระบบส่งข้อมูลให้ผู้ใช้ เช่น:

- ข้อมูลห้อง
- ประเภทห้อง
- ความจุ
- อุปกรณ์
- สิ่งอำนวยความสะดวก
- เงื่อนไขการใช้งาน
- กติกาการจอง

#### External Data Source → ระบบ V1

ระบบสามารถรับ:

- ข้อมูลห้องที่มีอยู่เดิม

V1 ยังไม่สร้างหรือแก้ไขข้อมูลต้นทาง และยังไม่มีการทำรายการจองจริง

## V2 – Room Availability Search

### Objective

V2 มุ่งเน้นการเพิ่มความสามารถในการค้นหาห้องที่ว่างตามเงื่อนไขที่ผู้ใช้ต้องการ โดยต่อยอดจาก V1 ที่สามารถแสดงข้อมูลและรายละเอียดของห้องได้

ผู้ใช้สามารถระบุวันที่ เวลา ความจุ และประเภทห้อง เพื่อค้นหาห้องที่ตรงตามเงื่อนไขและไม่มีการใช้งานซ้อนในช่วงเวลาที่เลือก

### In Scope

ผู้ใช้สามารถ:

- เลือกวันที่ต้องการใช้ห้อง
- ระบุเวลาเริ่มต้น
- ระบุเวลาสิ้นสุด
- ระบุจำนวนผู้ใช้งานหรือความจุที่ต้องการ
- เลือกประเภทห้อง
- ค้นหาห้องตามเงื่อนไขที่ระบุ
- ดูรายการห้องที่ตรงตามเงื่อนไข
- ตรวจสอบว่าห้องว่างในช่วงเวลาที่เลือกหรือไม่
- เลือกห้องจากผลการค้นหาเพื่อดูรายละเอียดของห้อง

ระบบจะใช้ข้อมูลตารางการใช้งานห้องเพื่อช่วยตรวจสอบว่าห้องมีการใช้งานในช่วงเวลาที่ผู้ใช้เลือกหรือไม่

### Out of Scope

ฟังก์ชันต่อไปนี้ยังไม่อยู่ใน V2:

- การเข้าสู่ระบบและ Authentication
- User Account
- การสร้างรายการจอง
- การแก้ไขรายการจอง
- การยกเลิกรายการจอง
- การอนุมัติการจอง
- การจัดการข้อมูลห้องโดย Admin
- การบันทึก Check-in / Check-out
- การบันทึก No-show
- การบันทึก Actual Usage
- การวิเคราะห์ Utilization
- Dashboard สำหรับผู้ดูแลหรือผู้บริหาร
- Notification

ฟังก์ชันเหล่านี้จะพัฒนาตาม Requirements ของ Version ถัดไป

### Assumptions / To Validate

- ข้อมูลตารางการใช้ห้องสามารถจัดเก็บใน Database ได้
- ข้อมูลตารางการใช้ห้องมีข้อมูลวันที่และช่วงเวลาการใช้งาน
- ข้อมูล Room Schedule สามารถเชื่อมโยงกับข้อมูลห้องที่มีอยู่ใน V1 ได้
- กฎในการตรวจสอบช่วงเวลาที่ทับซ้อนกันสามารถกำหนดได้อย่างชัดเจน
- สถานะห้องว่างใน V2 เป็นการคำนวณจากข้อมูล Schedule ที่มีอยู่ในระบบ
- V2 ยังไม่สร้างรายการจองจริงจากการค้นหาห้อง

### Data Ownership / Source of Truth

- V2 ยังคงใช้ข้อมูลห้องจาก Database ของ V1
- ข้อมูลประเภทห้องและข้อมูลห้องยังคงใช้จากตาราง room_types และ rooms
- V2 เพิ่มข้อมูลตารางการใช้ห้องใน room_schedules
- room_schedules ใช้เป็นข้อมูลสำหรับตรวจสอบว่าห้องมีการใช้งานในช่วงเวลาที่ผู้ใช้ค้นหาหรือไม่
- ระบบ V2 ใช้ Database เป็นแหล่งข้อมูลหลักสำหรับการค้นหาห้องว่าง

### Boundary

#### Inside the System – V2

ระบบ V2 รับผิดชอบการ:

- รับเงื่อนไขการค้นหาห้อง
- รับวันที่ที่ต้องการใช้ห้อง
- รับเวลาเริ่มต้น
- รับเวลาสิ้นสุด
- รับความจุที่ต้องการ
- รับประเภทห้อง
- ค้นหาห้องตามเงื่อนไข
- ตรวจสอบข้อมูลการใช้งานห้อง
- ตรวจสอบช่วงเวลาที่มีการใช้งาน
- แสดงรายการห้องที่ตรงตามเงื่อนไข
- แสดงรายละเอียดของห้องที่ผู้ใช้เลือก

#### Outside the System – V2

สิ่งที่ยังอยู่นอกขอบเขตของ V2 ได้แก่:

- Authentication / Login
- การสร้างและจัดการการจอง
- การอนุมัติการจอง
- การจัดการข้อมูลห้องโดยผู้ดูแล
- การบันทึก Check-in / No-show
- การบันทึก Actual Usage
- การวิเคราะห์ Utilization
- Dashboard และสถิติการใช้ห้อง
- Notification
- Payment
- การสร้างหรือแก้ไขข้อมูลการจองโดยผู้ใช้

### External Actors

สำหรับ V2 มี External Actor หลักคือ:

- ผู้ใช้ทั่วไป — ค้นหาห้องที่ว่างตามวันที่ เวลา ความจุ และประเภทห้อง โดยไม่จำเป็นต้องเข้าสู่ระบบ

บทบาทอื่น เช่น นักศึกษา อาจารย์ เจ้าหน้าที่ และผู้ดูแลระบบ จะเข้ามามีบทบาทใน Version ถัดไป เมื่อระบบรองรับ Authentication, Reservation และ Management

### External Systems / Data Sources

V2 ใช้ข้อมูลจากระบบและแหล่งข้อมูลที่มีอยู่ใน V1 ได้แก่:

- Database
- Room Information
- Room Type Information
- Room Schedule Information

ระบบใช้ Database เป็นแหล่งข้อมูลหลักในการค้นหาห้องและตรวจสอบ Availability

### System Boundary

#### ผู้ใช้ → ระบบ V2

ผู้ใช้สามารถ:

- เลือกวันที่
- เลือกเวลาเริ่มต้น
- เลือกเวลาสิ้นสุด
- ระบุความจุ
- เลือกประเภทห้อง
- ส่งคำขอค้นหาห้อง
- ดูผลการค้นหา
- เลือกห้องเพื่อดูรายละเอียด

#### ระบบ V2 → ผู้ใช้

ระบบส่งข้อมูลให้ผู้ใช้ เช่น:

- รายการห้องที่ตรงตามเงื่อนไข
- หมายเลขห้อง
- ประเภทห้อง
- ความจุ
- ข้อมูลพื้นฐานของห้อง
- รายละเอียดห้อง

หากไม่พบห้องที่ตรงตามเงื่อนไข ระบบจะแสดงผลว่าไม่พบห้องที่ว่างตามเงื่อนไขที่เลือก

#### External Data Source → ระบบ V2

ระบบสามารถรับข้อมูล:

- ข้อมูลห้อง
- ข้อมูลประเภทห้อง
- ข้อมูลตารางการใช้ห้อง

โดยข้อมูลเหล่านี้ถูกใช้ในการค้นหาและตรวจสอบห้องว่าง

V2 เพิ่มความสามารถในการค้นหาห้องว่างตามวันที่ เวลา ความจุ และประเภทห้อง แต่ยังไม่มีการสร้างรายการจองจริง

## V3 – Room Reservation & Approval

### Objective

V3 มุ่งเน้นการพัฒนาระบบจองห้องอย่างเต็มรูปแบบ โดยเพิ่มระบบ Login และ Authentication เพื่อให้ผู้ใช้สามารถสร้างและจัดการรายการจองได้ รวมถึงรองรับกระบวนการอนุมัติการจองตามสิทธิ์ของผู้ใช้

### In Scope

ผู้ใช้สามารถ:

- เข้าสู่ระบบผ่าน TU API
- สร้างรายการจองห้อง
- ตรวจสอบรายการจองของตนเอง
- แก้ไขหรือยกเลิกรายการจองตามเงื่อนไข
- ตรวจสอบสถานะการจอง
- ตรวจสอบสิทธิ์ในการจองตามประเภทผู้ใช้

ผู้มีสิทธิ์อนุมัติสามารถ:

- ตรวจสอบคำขอจองที่รออนุมัติ
- อนุมัติหรือปฏิเสธคำขอจอง

ระบบรองรับ:

- การยืนยันตัวตนและการจัดการ JWT
- การกำหนดสิทธิ์การใช้งานตามบทบาทและระดับการศึกษา
- การตรวจสอบช่วงเวลาการจองเพื่อป้องกันการจองซ้อน

### Out of Scope

- การบันทึก Check-in / Check-out
- การบันทึก Actual Usage
- การจัดการ No-show แบบอัตโนมัติ
- การติดตามการใช้งานห้องจริงผ่านหน้า Admin Booking Monitoring
- การจัดการข้อมูลห้องผ่านหน้าเว็บสำหรับเจ้าหน้าที่
- การวิเคราะห์ Utilization และ Dashboard

ฟังก์ชันเหล่านี้จะพัฒนาต่อยอดใน V4 และ Version ถัดไป

### Assumptions / To Validate

- TU API สามารถใช้ยืนยันตัวตนและดึงข้อมูลผู้ใช้ได้
- ข้อมูลผู้ใช้สามารถนำมาใช้กำหนดสิทธิ์ในการจองได้
- ระบบสามารถตรวจสอบช่วงเวลาที่ทับซ้อนกันก่อนสร้างรายการจอง
- ผู้อนุมัติและผู้ดูแลระบบมีสิทธิ์แตกต่างกันตามบทบาท

### Data Ownership / Source of Truth

- ข้อมูลผู้ใช้และการยืนยันตัวตนอ้างอิงจาก TU API
- ข้อมูลการจองและสถานะการจองจัดเก็บใน Database
- ข้อมูลห้องและประเภทห้องใช้จากตาราง rooms และ room_types
- ข้อมูลสิทธิ์ผู้ใช้จัดเก็บและตรวจสอบผ่านข้อมูล Roles และ Policies ใน Database

### Boundary

#### Inside the System – V3

- Authentication / Login
- การสร้างและจัดการรายการจอง
- การตรวจสอบสถานะการจอง
- การอนุมัติและปฏิเสธคำขอจอง
- การตรวจสอบสิทธิ์ผู้ใช้
- การตรวจสอบช่วงเวลาการจอง

#### Outside the System – V3

- การบันทึก Check-in / No-show
- การบันทึก Actual Usage
- การติดตามการใช้งานจริง
- การจัดการข้อมูลห้องผ่านหน้าเว็บ
- การวิเคราะห์ Utilization

### External Actors

- นักศึกษา — ค้นหาและจองห้องตามสิทธิ์
- อาจารย์ — ค้นหาและจองห้องตามสิทธิ์
- ผู้อนุมัติ (APPROVER) — ตรวจสอบและอนุมัติคำขอจอง

## V4 – Room Reservation & Utilization Management

### Objective

V4 มุ่งเน้นการต่อยอดระบบจองห้องให้รองรับการใช้งานจริงมากขึ้น ครอบคลุมการจัดการข้อมูลห้อง การค้นหาที่มีความยืดหยุ่น การติดตาม Actual Usage และการจัดการ No-show รวมถึงเพิ่มความปลอดภัยในการยืนยันตัวตน

### In Scope

ผู้ใช้สามารถ:

- ค้นหาห้องตามประเภท ความจุ อุปกรณ์ และช่วงเวลาที่ต้องการ
- ใช้ Filter อุปกรณ์ เช่น โปรเจกเตอร์ คอมพิวเตอร์ ทีวี และปลั๊กไฟ
- ค้นหาห้องอัตโนมัติเมื่อเลือกเงื่อนไข โดยไม่จำเป็นต้องกรอกครบทุกช่องหรือกดปุ่มค้นหา
- เพิ่มหมายเหตุเพิ่มเติมในการจอง
- ตรวจสอบรายการจองของตนเอง
- Check-in เพื่อบันทึกการเข้าใช้งานจริง
- End Usage เพื่อบันทึกเวลาสิ้นสุดการใช้งาน

ผู้ดูแลและเจ้าหน้าที่สามารถ:

- จัดการและปรับปรุงข้อมูลห้องผ่านหน้าเว็บ
- จัดการกติกาการจองและข้อมูลที่เกี่ยวข้องตามสิทธิ์
- ตรวจสอบรายการจองผ่านหน้า Admin Booking Monitoring
- ตรวจสอบข้อมูล Check-in, Actual Usage และ No-show

ระบบรองรับ:

- No-show Automation เมื่อผู้จองไม่ Check-in ภายใน 30 นาทีหลังเวลาเริ่มจอง
- การปรับสถานะห้องให้กลับมาว่างเมื่อเกิด No-show ตามเงื่อนไข
- การปรับปรุง Authentication และการจัดเก็บ JWT ผ่าน HttpOnly Cookie
- การตรวจสอบสิทธิ์ก่อนดำเนินการต่าง ๆ
- การทดสอบความถูกต้องของข้อมูลเมื่อมีผู้ใช้จองพร้อมกัน (Concurrency Testing)

### Out of Scope

- การวิเคราะห์ Utilization เชิงลึก
- Dashboard สถิติการใช้งานห้องสำหรับผู้บริหาร
- การวิเคราะห์และคาดการณ์ความต้องการใช้ห้อง

ฟังก์ชันเหล่านี้สามารถพัฒนาต่อยอดใน Version ถัดไป

### Assumptions / To Validate

- ข้อมูลห้องและอุปกรณ์ได้รับการอัปเดตอย่างถูกต้อง
- ระบบสามารถตรวจสอบการจองที่ทับซ้อนกันได้
- ระบบสามารถบันทึกเวลา Check-in และ Actual Usage ได้
- ระบบ No-show ทำงานตามเวลาที่กำหนด
- การจัดการข้อมูลห้องและกติกาการจองต้องเป็นไปตามสิทธิ์ของผู้ใช้
- ระบบต้องรองรับการใช้งานพร้อมกันและรักษาความถูกต้องของข้อมูล

### Data Ownership / Source of Truth

- ข้อมูลผู้ใช้และการยืนยันตัวตนอ้างอิงจาก TU API
- JWT Session จัดเก็บผ่าน HttpOnly Cookie
- ข้อมูลห้องและประเภทห้องจัดเก็บใน rooms และ room_types
- ข้อมูลการจองและสถานะจัดเก็บใน bookings
- ข้อมูลสิทธิ์ผู้ใช้จัดเก็บใน roles, user_roles และ Policies
- ข้อมูล Actual Usage และ No-show จัดเก็บในข้อมูลการจองเดิมผ่านฟิลด์ที่เกี่ยวข้อง
